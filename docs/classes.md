# クラス構成（決定済）

`Design.md` §8 #3 の詰め作業の成果。初回ローンチのクラス構成、シグネチャ・リソース、初期デッキ、戦闘の意味付け、将来クラスの計画を確定する。

## 参照する設計原則

- `Design.md` §1: 広く浅くインデックス、unknown unknowns に出会う
- `Design.md` §3: クラス = 分野
- `Design.md` §4: 理解＝強さ直結、効果は意味に忠実
- `Design.md` §5: 動く図（点・線・粒の動き）

## 決定1: 初回ローンチは 1 クラスのみ

- 個人開発 × C# 経験浅 × 操作型クイズ未試作の三重制約下で、Slay the Spire の段階リリース（2→3→Watcher を1年）に合致
- §1「広く浅く」は Early Access での追加で達成する前提
- 「選ぶ余地」は Slay the Spire の Ascension 相当の難易度選択で補う

**却下案:**
- 2クラス並列: コスト2倍、バランス調整が組合せで爆発
- 3クラス全部: 未完の野心作リスク、調査で回避推奨

## 決定2: 最初のクラス = ネットワーク

- §5「動く図」との相性が圧倒的（パケット/ハンドシェイク/ロードバランサ等が「粒の動き」と完全一致）
- カードの題材密度が高い（DNS / TCP-IP / サーキットブレーカー / リトライ / バックオフ 等 20-30 概念）
- 概念の離散性が高くカード化しやすい
- 将来クラスへの自然な導線（DB → 設計 → 要件定義）

**却下案:**
- DB から: 動く図適合度は高いがネットワークほどではない
- 設計から: 構造図主体で §5 と相性悪い
- 要件定義から: メタ概念で動く図にしにくい

## 決定3: シグネチャ・リソース = パケット

Slay the Spire の Orb / Poison / Stance 相当の固有リソース。

- 粒として生成・転送・遮断・フィルタ・滞留
- **§5「粒が流れる」と完全一致** = 操作型クイズの中核と直結
- カード化が無限（パケット生成 / 転送 / 遮断 / 優先度 / ルーティング等）
- Slay the Spire 流の "1クラス1リソース" 原則に従う

**却下案・保留:**
- コネクション状態 (state machine): 初回は1リソースに絞る、将来拡張候補
- パケット主 + コネクション補助 (レイヤード): 2リソース管理は初回には重い

## 決定4: 戦闘の意味付け = 案 2a「Slay the Spire 流戦闘 + 障害シナリオ翻訳」

戦闘構造は Slay the Spire 流（HP / ターン / ブロック）のまま、ナラティブと敵の意味付けだけ翻訳。

**敵の意味付け:**
- 敵 = ネットワーク障害シナリオの代理（過負荷サーバ / 攻撃トラフィック / リクエスト殺到 等）

**ナラティブ翻訳:**
- "敵HPを削る" = "障害源を弱体化させる / 障害の勢いを削ぐ"
- "敵を倒す" = "障害を鎮圧する / トラフィックを捌ききる"
- "戦闘勝利" = "ネットワークの安定を取り戻す"

**理由:**
- §4「意味に忠実」を戦闘構造まで貫徹、学習接続が深まる
- Slay the Spire の戦闘メカニクスは10年で "面白い" が検証済み、安全マージン

**却下案:**
- 案①（語彙のみ翻訳）: 学習接続が浅い
- 案 2b（戦闘ロジック自体再設計、HP無し / "問題解決で勝利"）: 未試作段階で大きな賭け、参考事例少ない → 将来検討項目として保留

## 決定5: 初期デッキ = 10枚、jobs 設計

| Job | カード仮名 | 役割 | 枚数 |
|---|---|---|---|
| **基本対処** | "Probe Request" 系 | パケット送信で障害源を1点弱化 | 4 |
| **基本遮断** | "Packet Filter" 系 | 受信パケット遮断、ブロック生成 | 3 |
| **状況把握** | "Lookup" 系 | カード1枚ドロー | 2 |
| **シグネチャ** | "Echo Reply" 系 | パケット複製で複数効果（クラスの方向性提示） | 1 |
| **合計** | | | **10** |

**jobs 名翻訳（Slay the Spire 流から Grimoire 文脈へ）:**
- 攻撃 → 対処/緩和
- 防御 → 遮断/フィルタ
- ドロー → 状況把握/探索
- シグネチャ → 基盤強化

**設計原則:**
- アーキタイプは強制しない（Mega Crit GDC 2019 知見）
- 中盤戦闘（Act 1 終わり相当）でアーキタイプが自然に定まる導線
- **具体カード名・パラメータは試作で詰める**（今は役割と枚数のみ確定）

**却下案:**
- 8枚: シャッフル頻度高く飽きやすい
- 12枚: ラーニングカーブが急

## 決定6: ラン構造（暫定）

§2「気が向いたとき 1回 10-15分」から逆算した暫定値。**試作で実測して調整**。

- 1ラン = 5-7戦闘 + ボス1
- カード入手機会 5-7回
- ラン終了時のデッキ規模 = 15-17枚
- Slay the Spire（1ラン1-2時間、デッキ25-30枚）の約半分のスケール

## 決定7: 将来クラスの計画（最小版）

**2クラス目候補: DB**
- ネットワークの隣接領域、動く図適合度が高い
- インデックス検索 / ロック相互排他 / トランザクション等の動きを表現可

**3クラス目以降:** ユーザーニーズ次第（設計 or 要件定義）。設計クラスは §5 動く図の方針改訂が必要になる可能性あり。

**追加タイミング:** 時期固定しない。判断基準ベース:
- 初回リリース後、最低限のバグ修正と動作安定化が完了
- 1ラン分の体験フィードバックを最低 5-10 件収集
- 「動く図 × 操作型クイズ」のパターンが安定している

## 試作で検証すべきこと

- カード手札の配置・サイズ感
- 動く図の戦闘画面でのスケール
- 操作型クイズのテンポ感
- 「障害シナリオ」ナラティブが機能するか
- 初期デッキ10枚の配分（4-3-2-1）が短いランで成立するか
- 短縮版／自動発動の UI 動作（[`quiz-cadence.md`](quiz-cadence.md) と連動）
- ラン構造（5-7戦闘）の長さ感
- アーキタイプ強制なしで中盤に自然に方向性が定まるか

## 将来検討項目（範囲外、保留）

- 案 2b への進化（戦闘ロジック自体再設計、"問題解決で勝利"）: 2a 試作で必要性が見えてから判断
- コネクション状態をシグネチャ・リソースに追加（パケット + コネクションのレイヤード設計）
- 3クラス目以降の具体（設計 / 要件定義）
