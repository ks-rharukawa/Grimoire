# カード操作デザイン（最初の4 job）

`quiz-cadence.md` 決定1「基本形＝操作型」と `classes.md` 決定5「初期デッキ10枚・4 job」を、**実装可能な操作仕様**に落とす派生スペック。`style-guide.md` と同じく「実装のソース・オブ・トゥルース」系（§8 未決事項ではなく、決定済み原則の具体化）。

> **位置づけ:** これは `quiz-cadence.md` が *「未検証コスト: 全カード分の操作デザイン → 最初の3-5枚で現実性を試作検証する」* と名指しした項目、かつ `classes.md` が *「具体カード名・パラメータは試作で詰める」「操作型クイズのテンポ感」* と保留した項目の詰め作業。原則は動かさず、4 job 分の「操作アーキタイプ」を確定する。

## 参照する確定事項（蒸し返さない）

- `quiz-cadence.md` 決定1: 操作型 = 動く図を正しい状態にする使用時チェック
- `quiz-cadence.md` 決定2: 習熟で軽量化（初回フル → 正解後短縮 → 一定戦闘後フル復活）
- `quiz-cadence.md` 決定3: 失敗時シンプル不発（敵によっては暴発自傷）
- `quiz-cadence.md` 決定4: **理解難度が主軸**、操作難度は補助（アクセシビリティ調整可）、使用制限は最強帯のみ
- `classes.md` 決定3: シグネチャ・リソース = パケット（粒）
- `classes.md` 決定5: 初期デッキ **合計10枚** = 4 job（基本対処4 / 基本遮断3 / 状況把握2 / シグネチャ1）
- `classes.md` 障害状態語彙: 過負荷 / 輻輳 / 欠落 (Packet Loss) / 遅延 / 攻撃流量 / 名前解決失敗 (DNS Failure)
- `Design.md` §5: 動く図の3層構造（対応表 / 字幕 / 操作時説明）

## 設計単位 = job（カードではなく操作アーキタイプ）

初期デッキは **合計10枚** = 4 job × 複数枚（4-3-2-1、`classes.md` 決定5 と一致）。同 job のカードは操作を共有し、**パラメータ（弱化量・ブロック量・コスト）のみ変える**。よってここで設計するのは **4 つの操作アーキタイプ**＝「最初の3-5枚」の検証対象そのもの。

## ガード: なぜ「操作」が Q&A 型に退化しないか

quiz-cadence 決定1 は Q&A 型を却下した（戦闘を止める＝チョコがけブロッコリー）。以下の操作が Q&A／「色付き正解クリック」に退化しないための**3条件**を定義する（reviewer / codex レビューの収束指摘を反映）。

| 条件 | 内容 | 退化の例（禁止） |
|---|---|---|
| **A. 正解は動く図の状態から読む** | 正解は静的な問題文でなく、毎フレーム変化する図（粒の流れ・応答遅延・キャッシュ状態）から読み取る | 固定の選択肢ボタン |
| **B. 正解根拠は概念上の因果から導く** | 「なぜそこが正しいか」が概念の因果・状態遷移で説明できる。**色やラベルで正解を露出しない**（色は命中後のフィードバックに限定） | 赤い場所＝正解、と色で教える |
| **C. 図への直接操作** | 入力は図の要素（ノード/経路/粒）への操作で、効果が連動発火 | 図は飾りでボタンを押すだけ |

`Design.md` §4「ノードに配置する等の操作」「粒の流れを止める／線を引く」の範囲内。**条件 B が本仕様の肝**：動いていても答えが色・ラベルで露出していれば実質 Q&A なので、各アーキタイプは「概念を理解していないと因果が読めない」よう設計する。

## 操作アーキタイプ 1: 基本対処「Probe Request」系（4枚 / 理解難度: 低）

- **概念**: probe（生存・負荷確認の小さなパケット）を送り、**応答から**障害源を診断して弱化する。
- **変える障害状態**: 過負荷 (Overload) / 攻撃流量 (Attack Traffic) を 1 段弱化。
- **動く図**: 敵＝過負荷サーバ。複数の処理スロットが**見た目は同一**で並ぶ（過負荷スロットを色で露出しない＝条件B）。
- **正しい状態を作る操作**: probe 粒を各スロットへ送り、**返ってくる応答のサイン**（応答遅延 / キュー滞留 / 無応答＝タイムアウト）を観測して、過負荷スロットを特定し対処する。
  - **理解難度（主）**: probe の応答から負荷状態を読む（＝probe の意味そのもの）。「速い応答＝健全 / 遅い・返らない＝過負荷」という因果を理解していないと特定できない。
  - **操作難度（補助）**: probe 送信と対処の選択。精度はアクセシビリティで当たり判定拡大可。
- **成功判定**: 応答が過負荷を示すスロットへ対処 → 効果発動（敵HP −N かつ過負荷を1段弱化）。
- **失敗時**: 健全（応答が速い）スロットへ対処＝診断ミス → シンプル不発（決定3）。ターン消費、カードは捨て山へ。
- **習熟軽量化（決定2）**: 一度正解 → 次から probe 応答が即時表示・自動特定、クリック1回で発動。一定戦闘経過でフル観測復活。
- **§5 3層**:
  1. 対応表: 左＝自App ／ 金粒＝probe ／ 右＝サーバの処理スロット ／ 応答の速さ＝そのスロットの負荷
  2. 字幕: 「probe 送信、応答を観測中…」→ 命中「応答遅延を検知、過負荷源を特定して弱化」
  3. 操作時説明（知の呪い回避型）: ①「ping と同じで“相手を攻撃する”ものではない」→ ②「health check と同じ生存・負荷確認」→ ③「probe = 応答の有無/遅延で相手の負荷状態を知る」→ ④「リクエスト本体を送る通常通信とは違い、確認が目的」

## 操作アーキタイプ 2: 基本遮断「Packet Filter」系（3枚 / 理解難度: 中）

- **概念**: 受信トラフィックを**動きのパターンで選別**し、悪性だけを遮断してブロックを生成する。
- **変える障害状態**: 攻撃流量 (Attack Traffic) / 輻輳 (Congestion) を予防。
- **動く図**: 敵→自App へ複数の流れ。**悪性/良性を色で露出しない**（条件B）。悪性は動きで現れる：同一送信元からのバースト（連続殺到）/ 経路圧迫 / 不自然な等間隔連続。良性は散発的で送信元が多様。
- **正しい状態を作る操作**: 流れのパターンを観測し、フィルタを**悪性のバースト経路に置いて遮断し、散発的な良性は通す**（全遮断は誤り＝フィルタの本質は選別）。
  - **理解難度（主）**: 攻撃流量のパターン（集中・バースト）を正常通信（散発・多様）と**動きで**見分ける。色のヒントなしで因果（なぜ悪性か）を読む。
  - **操作難度（補助）**: フィルタ配置の1〜2ステップ。
- **成功判定**: 悪性のみ遮断 → Block +N 生成、攻撃流量/輻輳を予防。
- **失敗時**: 良性まで遮断 or 悪性を通す → シンプル不発。
- **習熟軽量化**: 正解後はパターン判定が補助表示され、配置1クリックで発動。
- **§5 3層**:
  1. 対応表: 経路上の粒の**動き方**＝トラフィックの性質（バースト＝攻撃 / 散発＝正常）／ ゲート＝フィルタ
  2. 字幕: 「バーストを検知、悪性トラフィックを選別遮断してブロック生成」
  3. 操作時説明: ①「ファイアウォール＝“全部遮断”ではない」→ ②「メールのスパムフィルタと同じ選別」→ ③「条件（パターン）に合う通信だけ落とす」→ ④「物理的に線を切る遮断とは違い、選別して残す」

## 操作アーキタイプ 3: 状況把握「Lookup」系（2枚 / 理解難度: 中）

- **概念**: DNS lookup の**解決プロセス**（キャッシュ→TTL→権威）をたどって名前を解決し、情報（カード）を引く。
- **変える障害状態**: 名前解決失敗 (DNS Failure) / 欠落 (Packet Loss) を解消。
- **動く図**: 未解決の名前ノードと、解決経路（ローカルキャッシュ / 権威サーバ）。**正解は静的な名前→IP 対応ではなく、図の動的状態から導く**（条件B、Q&A退化の最右翼への対策）：
  - キャッシュに**有効な**エントリがある（TTL 残あり）→ キャッシュから即解決が正解
  - キャッシュが **TTL 切れ**（カウントダウンが 0）→ 権威サーバへ問い合わせるのが正解
  - 権威が NXDOMAIN を返す状態 → 「解決不能」と判断するのが正解（無理に問い合わせ続けると失敗）
- **正しい状態を作る操作**: 図のキャッシュ/TTL 状態を読み、**正しい解決経路**を選んでつなぐ。
  - **理解難度（主）**: 「キャッシュが効くか／TTL が切れているか／権威に存在するか」という解決プロセスの理解。TTL 表示が動的に変わるので毎回読み直す。
  - **操作難度（補助）**: 経路接続の1ステップ。
- **成功判定**: 状態に合った経路で解決 → カード +1 ドロー、名前解決失敗を解消。
- **失敗時**: TTL 切れを見落としキャッシュ参照 / NXDOMAIN を問い合わせ続ける → 不発（ドローなし）。
- **習熟軽量化**: 正解後は解決経路が即時提示、クリック1回でドロー。
- **§5 3層**:
  1. 対応表: ?ノード＝未解決の名前 ／ TTL バー＝キャッシュの残り有効時間 ／ 権威＝最終的な答えの持ち主
  2. 字幕: 「キャッシュ TTL 切れ、権威へ問い合わせて解決」等、状態に応じて変化
  3. 操作時説明: ①「DNS＝“ネットを速くするもの”ではない」→ ②「電話帳：名前から番号を引く」→ ③「キャッシュ→TTL→権威の順で名前を解決」→ ④「データ本体を運ぶ通信とは別、宛先を知る前段」

> **試作の最優先（codex/reviewer 収束）**: lookup は4 job 中で最も静的マッチング（Q&A）へ退化しやすい。TTL カウントダウン等の**動的状態が無いと解けない**設計になっているかを最初に実機検証する。

## 操作アーキタイプ 4: シグネチャ「Echo Reply」系（1枚 / 理解難度: 高）

- **概念**: `classes.md` 決定5 のとおり「パケット複製で複数効果」。シグネチャはクラスの方向性提示。
- **変える障害状態**: 複数状態を同時操作（`classes.md` 対応表）。
- **動く図**: **自己完結型**（reviewer 指摘反映）。echo 専用に、図の中に複数の対処対象（過負荷源・滞留経路 等）を**このカード自身が内包**する。他アーキタイプの図要素や、その戦闘で引いた他カードには依存しない（習熟軽量化で他カードの図が簡略化されていても成立する）。
- **正しい状態を作る操作**: 複製した echo 粒を、図内の**複数の正しい対象へ同時に正しく**振り分ける。
  - **理解難度（主）**: 複数の「正しい状態」を一度に判断する（最も高い理解難度 → 決定4 主軸により最強帯）。
  - **器用さへ寄らない制約（codex 指摘反映）**: **判断対象の数が難度**であって手数ではない。順不同・ドラッグ精度不問・時間制限なしを既定とし、「複数ステップだから強い」設計を禁止する。
- **成功判定**: 全対象が正しい → 複合効果（例: 敵HP削り＋Block＋状態弱化）。
- **部分成功**: **プロトタイプは「全対象正解で発火、1つでも誤れば全不発」で開始**（codex 指摘＝初期値固定）。部分発火を入れるかは試作で判定。
- **失敗時**: 不発。決定4 従軸の使用制限（Exhaust / 1ラン1回）付与候補 → 試作で判定。
- **習熟軽量化**: 高理解難度のため自動化は最後（forgetting-curve の再フル操作対象として優先度高）。
- **§5 3層**:
  1. 対応表: echo 粒＝複製パケット ／ 分岐＝複数対象への振り分け
  2. 字幕: 「パケットを複製し、複数の障害に同時対処」
  3. 操作時説明: ②「ping の応答側／やまびこ」→ ③「受けた要求に応答を返す（ICMP Echo Reply）」を軸に、複製メカニクスとの橋渡しを字幕で示す

> **名前と概念の忠実性ギャップ（codex High 指摘 → 試作で名前を詰める）**: ICMP Echo Reply は本来「複製」でなく「要求への応答」。`classes.md` はカード名を**仮名**とし「具体カード名は試作で詰める」としているため、複製メカニクスを保つなら名前を `Packet Fan-out` / `Mirror` 系へ寄せる、または効果を「応答で到達性を証明し複数状態を確定」へ寄せる、の2択を試作で検証する。**`classes.md` 決定5 のメカニクス（複製で複数効果）自体は維持**し、ここでは名称の整合のみ未決として残す。

## 横断的決定

### 理解難度の段階と効果の強さ（決定4 整合）

| job | 理解難度 | 効果の強さ | 使用制限 |
|---|---|---|---|
| 基本対処 | 低 | 弱（単体弱化） | なし |
| 基本遮断 | 中 | 中（Block生成＋予防） | なし |
| 状況把握 | 中 | 中（ドロー） | なし |
| シグネチャ | 高 | 強（複合） | Exhaust 等を試作で判定 |

「正しい状態」を**読み解く**認知的難しさ＝効果の強さ。器用さ（精度・速度・手数）は強さに連動させない。

### アクセシビリティと失敗条件（quiz-cadence 準拠 / reviewer・codex 指摘反映）

- **時間制限**: ON/OFF。基本対処/遮断/把握は OFF 可（タイミングが概念の本質でないため）。
- **時間制限 OFF 時の失敗条件**: 「時間切れ」経路は消え、失敗は**誤操作（誤った状態を作った）のみ**で判定する。決定4「効果判定は理解難度のみ・アクセシビリティで不変」を守る。
- **暴発自傷（決定3）× 時間制限 OFF**: 初回4 job では敵の暴発トリガーは**「誤操作」失敗でのみ発火**し、時間切れには依存させない。よって時間制限 OFF でも暴発の被リスクは変わらない（OFF が有利／不利にならない）。（将来クラスでタイミングが本質のカードが入る場合、「時間切れ＝暴発」を別途設計する。）`style-guide.md` §10 の `⏱` icon で時間制限の ON/OFF を視覚提示。
- **操作精度**: 標準/緩和（ターゲット当たり判定の拡大）。
- **ステップ数**: 変更不可（理解の本質）。
- 初期4 job には**タイミング/精度が概念の本質のカードは存在しない**（quiz-cadence 決定4 例外条項の対象＝レースコンディション系は DB 寄りで、`classes.md` 決定7 の2クラス目以降）。よって初回クラスでは時間制限・精度は全てアクセシビリティで調整可。

### 失敗時の振り返り（quiz-cadence 決定3）

- 戦闘後、失敗したカードの「正しい操作シーケンス」を動く図で再生（テキスト長文は出さない）。
- 最低視聴時間 暫定3秒、スキップ可。

## 試作で検証すべきこと

- **[最優先] lookup が動的状態（TTL/キャッシュ）無しに解けないか** — Q&A 退化の最右翼（収束指摘）
- 4 job の操作がガード3条件（動く図 / 因果 / 直接操作）を満たし「色付き正解クリック」に退化しないか
- probe の応答サイン（遅延 / キュー滞留 / 失敗率）が**色非依存**で「読み取れる」難度になっているか（簡単すぎ＝作業、運/反射でなく**概念読解**で解けること）
- filter のバースト/散発パターンが色ヒント無しで見分けられるか、色覚多様性で機能するか（形状・動きでも区別、style-guide §10）
- probe スロット選択／filter 選別／lookup 接続の**当たり判定と許容範囲**の数値化
- 習熟軽量化（自動特定・即時化）の UI 動作とテンポ
- シグネチャの自己完結図に複数対象を収める表示と、部分成功（初期＝全不発）の妥当性
- シグネチャの名称 vs 複製メカニクスの概念忠実性（`Echo Reply` 仮名の再検討）
- §5 3層（対応表＋字幕＋動く図）が style-guide §5 レイアウト（Stage y=220-440）と §8 字幕制約（1行・32px）に収まるか
- `CombatView` の既存描画（サーバスロット表現等）が流用可能か実体確認（src/ の現状依存）
- 操作型の1ターン所要時間（10-15分/ラン の §2 制約に収まるか）
- アクセシビリティ調整時に効果判定が理解難度のみで成立するか
